# Evidence-driven self-correction

`RepairLoop(agent, verifier).run(initial_diagnosis, repository, limits, max_attempts=2)`
composes the existing proposal generator and `PatchVerifier`. Call `agent.analyze`
once before entering the loop. Diagnosis is not rerun between attempts. The normal
first candidate is generated by Nemotron; the correction prompt is used only after
observed test failure. The original repository is passed to every verification;
each verifier invocation creates its own disposable copy.

## Deterministic policy

The budget is a strict integer from 1 to 2 (default 2), checked before model or
Docker calls. A verified candidate stops immediately. Only an applied, valid
candidate with targeted-test or regression failure (pytest exit 1) can consume
the remaining correction attempt. Malformed/invalid proposals, application
failures, infrastructure failures, timeouts, source changes, cleanup failures and
integrity failures terminate immediately. A second test failure yields
`retry_exhausted`. There are no automatic model retries, new diagnoses, changed
limits, or security relaxations.

## Evidence and state

`RepairRun` contains the initial diagnosis, budget, terminal status/reason,
timestamps, every `RepairAttempt`, and final verification when available.
Each attempt retains its complete `PatchProposalAttempt` and `PatchVerification`
chain, outcome, and the sanitized `CorrectionEvidence` used to request it.
Records are in memory and JSON-serializable; persistence is left to callers.

Correction input contains original bounded context/diagnosis and limits, plus:

- Previous schema-valid proposal, including diff, expected behavior and risk notes.
- Previous verification status and changed files.
- Targeted/regression exit status, pass flag, up to ten failed IDs (300 characters
  each), and at most 2,000 characters per stdout/stderr excerpt.

It excludes command arrays, raw evidence objects, workspace paths and unbounded
logs. Known credentials, common secret assignments, and common host-path forms
are redacted. Entire request JSON is capped at 60,000 UTF-8 bytes, failing closed
if exceeded. Redaction is not a universal secret detector. Complete raw evidence
is retained locally for audit, not transmitted as correction input.

The separate correction prompt treats all evidence and previous model output as
untrusted data. It explicitly requests one revised patch against original source,
not the previous temporary copy. It forbids tests/config/secrets/dependency changes,
refactors and tool calls. Verification alone determines success. Existing patch
transport is preserved: `multiline=True`, JSON-object mode, thinking disabled,
strict local Pydantic validation; diagnosis behavior is unchanged.

This is evidence-driven because the next request contains the previous candidate
and its new observed failure, rather than simply repeating the initial prompt.
The existing validator and verifier remain authoritative. All previous sandbox,
path, argv, resource, timeout, and cleanup restrictions remain unchanged.

## Controlled real demo

```powershell
.\.venv\Scripts\python.exe -m scripts.test_self_correction
```

Requires the existing sandbox image, Docker Linux containers, and local Nebius
settings for `nvidia/Nemotron-3_5-Lightning`. The script-only `DemoAgent` injects
`return left * right` as candidate 1. This is deliberately safe but incorrect:
`add(2, 3)` produces 6 instead of 5. It passes the normal proposal validator, then
fails real Docker targeted testing. Failure is never simulated in this demo.
Candidate 2 comes from a real Nemotron request containing that verification
evidence and goes through unchanged validation and verification. The production
loop contains no injection option or fixture-specific logic.

The script reports the injection, exact two-attempt trajectory, statuses and test
results, original fixture hashes, cleanup, a SHA-256 digest of the correction
request at the client boundary, and the response model. The digest is an audit
correlation value, not a cryptographic attestation of remote processing. Exit 0
requires the expected failure then success, both final test stages passing,
original hashes unchanged and all workspaces cleaned. It never prints full
requests or credentials.

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_self_correction.py
.\.venv\Scripts\python.exe -m pytest
```

Unit tests use mocks; repository code never runs on the host. They also compose
the real verifier with a mocked Docker runner to check separate workspaces and
byte-for-byte original preservation across attempts.

## Limits

This is one Python fixture, not evidence of general autonomous repair reliability.
The fixture's existing tests are the verification scope; coverage may miss bugs.
The loop does not guarantee a different or correct second proposal. Its budget
is at most two candidates. Existing stable-checkout assumptions and small Python
fixture copy limits remain. Host crashes or daemon outages can prevent resource
cleanup; reported cleanup/integrity failures stop correction. No UI, database,
GitHub integration, dependency installation, ingestion or benchmark system is added.
